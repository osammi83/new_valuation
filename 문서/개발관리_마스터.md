# 03.new_valuation 개발관리 마스터

이 문서는 `03.new_valuation`의 개발 일정, 개발 이력, 웹 전환, GitHub 자동화, 백필 계획, 운영 메모를 한 곳에서 관리하는 단일 기준 문서다.

새로운 개발 요청이 들어오면 다른 문서를 추가로 만들지 말고 이 문서에 다음 순서로만 갱신한다.

1. 현재 상태 요약
2. 개발 일정과 우선순위
3. 백로그와 다음 작업
4. 개발 이력
5. GitHub/web/백필 자동화 항목
6. 검증 결과와 완료 조건

## 1. 현재 상태 요약

- 로컬 Windows + PowerShell 기반 daily 파이프라인은 정상 동작한다.
- `program/python/run_pipeline.py`는 일일 실행의 표준 진입점이다.
- `publish_to_drive.py`는 검증 후 업로드와 `publish_history.csv` 기록을 수행한다.
- `train_models.py`는 baseline 학습과 active/inactive registry 관리를 수행한다.
- UTF-8 BOM 기준으로 CSV 저장 정책을 정리했다.
- GitHub 자동 동기화와 웹 전환 골격을 추가했다.
- 공용 Streamlit은 조회 전용으로 정리했고, 생성은 GitHub Actions와 Drive 저장으로 분리한다.
- 웹 조회/실행 진입점과 5일 소량 백필 테스트가 준비됐다.
- `ops_admin.py github-check`로 GitHub 준비 상태를 점검할 수 있다.

### 운영 설정 점검

- `pythonPath`는 로컬 venv 경로로 설정돼 있다.
- `enableGithubAutoSync`는 `true`다.
- `enableGoogleDriveUpload`는 `false`다.
- `googleDriveFolderId`와 `googleServiceAccountJsonPath`는 아직 비어 있다.
- `krxId`와 `krxPw`는 아직 비어 있다.
- 운영 배포에 필요한 비밀값은 아직 GitHub Actions와 로컬 설정에 추가 정리가 필요하다.

### 6-1. 공용앱 배포 방식

공용앱은 로컬 Windows 실행기가 아니라, GitHub 저장소와 연결된 Streamlit 앱으로 배포한다.

권장 배포 플랫폼:

- Streamlit Community Cloud
- 또는 다른 Python 호스팅 서비스(비슷한 방식으로 설정 가능)

배포 시 핵심 원칙:

- 앱은 `program/web/streamlit_app.py` 를 메인 진입점으로 둔다.
- 앱 내부의 `PUBLIC_APP_MODE=true` 로 로컬 Windows 전용 실행 버튼을 숨긴다.
- 공용앱은 직접 `run_pipeline.py daily` 를 돌리지 않는다.
- 공용앱은 GitHub Actions workflow_dispatch 를 호출하는 버튼만 제공한다.

### 6-2. 공용앱 세팅 순서

1. GitHub 저장소를 Streamlit Cloud에 연결한다.
2. Repository / Branch / Main file path 를 지정한다.
3. Main file path 는 `program/web/streamlit_app.py` 로 둔다.
4. Streamlit Cloud Secrets 에 아래 값을 등록한다.
	- `PUBLIC_APP_MODE=true`
	- `GITHUB_REPO_SLUG=owner/repo`
	- `GITHUB_TOKEN` 또는 `GH_TOKEN`
5. GitHub 저장소 Settings > Secrets and variables > Actions 에 아래 값을 등록한다.
	- `DART_API_KEY`
	- `KRX_ID`
	- `KRX_PW`
	- `GOOGLE_DRIVE_FOLDER_ID`
	- `GOOGLE_SERVICE_ACCOUNT_JSON`
6. GitHub Actions 워크플로우가 필요하면 `.github/workflows/auto-sync.yml`, `.github/workflows/backfill_5y.yml` 를 사용한다.
7. 앱이 열리면 실행 탭에서 `GitHub Actions 실행` 버튼만 사용한다.

### 6-2-1. 버튼별 의미

- `GitHub Actions 실행`: 선택한 workflow_dispatch 를 원격 GitHub에서 실행한다.
- `backfill_5y.yml`: 5년치 백필을 GitHub Actions에서 생성한다.
- `auto-sync.yml`: 일일 산출물을 만든 뒤 GitHub로 다시 푸시한다.
- `ci.yml`: 문법/BOM 검증용이며 일반 사용자가 자주 누를 버튼은 아니다.

### 6-3. 공용앱에서 무엇을 실행하는가

- `auto-sync.yml`: 일일 실행 후 GitHub로 소스 반영
- `backfill_5y.yml`: 과거 5년치 백필 생성
- `ci.yml`: 수동 검증 또는 PR 검증

공용앱에서는 다음을 실행하지 않는다.

- 로컬 `program/python/run_pipeline.py daily`
- 로컬 `program/powershell/sync_github.ps1`
- Windows Task Scheduler 등록 스크립트

### 6-4. 사용자가 실제로 누를 버튼

공용앱 기준:

1. 실행 탭은 조회 안내만 확인한다.
2. GitHub 저장소에서 workflow_dispatch 를 실행한다.
3. 완료 후 이 앱에서 Google Drive 결과를 확인한다.

로컬 관리자 화면 기준:

1. `program/powershell/run_web.ps1` 로 대시보드를 실행한다.
2. 실행 탭에서 로컬 실행 또는 GitHub 반영을 선택한다.
3. 관리 화면은 운영자가 직접 돌릴 때만 사용한다.

## 7. 5년치 백필

목표는 과거 5년치 날짜를 순회하며 daily 산출물을 쌓고, 현재와 과거를 같은 계약으로 비교하는 것이다.

권장 방식:

- 날짜 오버라이드 가능한 backfill runner 생성
- 결과를 날짜별 CSV 또는 누적 저장소로 축적
- 백필과 daily를 같은 오케스트레이터에서 호출 가능하게 분리
- `program/python/history_backfill.py`와 `backfill_5y.yml`로 소량/장기 백필 모두 실행 가능

## 8. 관리 원칙

- 새 문서는 만들지 않는다.
- 새 작업은 반드시 이 문서에 먼저 기록한다.
- 하위 문서는 필요 시 이 문서를 참조만 하게 한다.
- 검증 결과를 먼저 적고, 다음 작업을 이어 적는다.
- GitHub 자동화가 실패해도 로컬 daily 파이프라인은 실패시키지 않는다.
