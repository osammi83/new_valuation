# 03.new_valuation 재분석 프로그램 설명서 v1.1

## 1. 판단 기준
이 문서는 첨부된 `deep-research-report_v1.1.md`를 기준으로, 현재 `03.new_valuation` 시스템에서 각 개발 항목을 `가능`, `조건부 가능`, `보류`, `제외`로 구분한 재분석 문서다.

판단 원칙은 다음과 같다.

- `가능`: 현재 코드베이스와 CSV-first 구조만으로 구현 가능
- `조건부 가능`: 구현은 가능하지만 외부 데이터 품질, 인증, 히스토리 축적, 또는 대규모 리팩터가 필요
- `보류`: 현재 시스템에는 있으나, 즉시 확장하기보다 단계적 전환이 필요한 항목
- `제외`: 개발 범위에서 제외하기로 한 항목

## 2. 현재 시스템 요약
현재 시스템은 PowerShell 오케스트레이션과 Python 배치 처리로 동작하는 CSV 중심 구조다.
핵심 흐름은 대략 다음과 같다.

- `run_daily.ps1`가 일일 실행을 오케스트레이션한다.
- `preprocess_daily_updates.py`가 공시 기반 전처리와 EPS 보정의 일부를 처리한다.
- `refresh_assumptions.py`가 `universe.csv`와 `assumptions.csv`를 정합화한다.
- `refresh_eps_cache.py`가 EPS 캐시를 갱신한다.
- `build_daily_report.py`가 점수, 액션, 비중, 리포트를 생성한다.
- `upload_to_google_drive.py`가 선택적으로 결과를 Drive에 게시한다.

즉, 현재 구조는 이미 `CSV 파일을 중간 계약으로 쓰는 단일 배치 시스템`에 가깝다. 그래서 v1.1이 요구하는 모듈화 자체는 가능하지만, 실제로는 `기존 거대한 리포트 엔진을 역할별로 분해`하는 작업이 핵심이다.

## 3. 가능성 판단
### 3.1 바로 가능한 항목
아래 항목은 현재 코드와 데이터 흐름만으로도 구현 가능하다.

- `schema_registry.csv`
- `validate_csv_contracts.py`
- `sync_universe_master.py`
- `ingest_dart_disclosures.py`
- `build_features_daily.py`
- `score_daily_signals.py`
- `manage_positions.py`
- `validate_outputs.py`
- `publish_to_drive.py`
- `ops_admin.py`
- `run_history.csv`, `error_log.csv`, `model_registry.csv` 같은 운영 메타 CSV

이 범주는 현재 프로젝트가 이미 `pandas + CSV + PowerShell` 기반으로 돌아가고 있기 때문에 가장 자연스럽다.

### 3.2 조건부 가능한 항목
아래 항목은 구현 가능하지만, 데이터 원천이나 운영 정책에 따라 품질이 달라진다.

- `ingest_market_data.py`
- `train_models.py`
- `backtest_walkforward.py`
- `build_features_daily.py`의 고도화 버전
- `manage_positions.py`의 실제 포지션 보관/복원 기능

조건부인 이유는 다음과 같다.

- 시세 원천의 일관성 문제
- DART, KRX, yfinance, FinanceDataReader의 결측/지연/포맷 차이
- 학습과 백테스트에 충분한 과거 데이터 축적 필요
- 실제 주문 연동이 아니라면 포지션 관리가 `시뮬레이션 중심`으로 제한됨

### 3.3 보류 또는 분리 권장 항목
아래는 불가능하다고 단정할 수는 없지만, 현재 구조에서 즉시 넣기보다 분리 설계가 우선이다.

- `run_daily.ps1`를 완전히 폐기하고 단일 Python 런처로 즉시 교체하는 것
- `build_daily_report.py`를 그대로 유지하면서 동시에 `build_features_daily.py`, `score_daily_signals.py`, `validate_outputs.py`까지 중복 없이 얇게 쪼개는 것
- `day1_validation.py` 같은 레거시 검증기를 그대로 계속 운영하는 것

이 항목들은 기술적으로는 가능하지만, 현 코드가 이미 하나의 엔진에 많은 책임을 담고 있어 `직접 대체`보다 `단계적 분리`가 더 안전하다.

### 3.4 개발 제외 항목
아래 항목은 현재 재분석의 개발 범위에서 제외한다.

- DB 중심 전환을 전제로 한 설계
- CSV를 포기하고 운영 체계를 전면 재작성하는 방식
- 외부 시스템 인증 없이 실시간 완전 자동 주문 집행까지 포함하는 범위 확장

현재 문서의 목표는 `CSV-first`를 유지하면서 운영성과 검증성을 높이는 것이므로, 이 방향은 개발하지 않는다.

## 4. 프로그램 역할 설명
### 4.1 오케스트레이션
- `run_pipeline.py`: 전체 실행 순서를 하나의 Python 진입점에서 제어하는 역할이다.
- `run_daily.ps1`: 기존 운영용 외곽 래퍼이며, 내부적으로 `run_pipeline.py`를 호출한다.
- `ops_admin.py`: 설치, 점검, 스케줄, 환경변수를 묶는 관리 CLI로 적합하다.

### 4.2 데이터 계약
- `schema_registry.csv`: 각 CSV의 스키마, 키, 필수 컬럼, enum 제약을 선언적으로 관리한다.
- `validate_csv_contracts.py`: 실제 파일이 계약을 만족하는지 검사한다.
- `validate_outputs.py`: 결과물의 행 수, 컬럼, 액션-비중 정합성을 확인한다.

### 4.3 데이터 적재
- `sync_universe_master.py`: universe와 assumptions를 같은 기준으로 맞춘다.
- `ingest_market_data.py`: 가격, 거래대금, 변동성, 수급 지표를 취합한다.
- `ingest_dart_disclosures.py`: 공시 기반 이벤트를 수집한다.

### 4.4 피처와 신호
- `build_features_daily.py`: 밸류, 모멘텀, 변동성, 섹터, 레짐 피처를 만든다.
- `score_daily_signals.py`: 피처와 규칙을 바탕으로 점수와 액션을 계산한다.
- `manage_positions.py`: 보유/편입/제외/비중/리밸런싱 상태를 관리한다.

### 4.5 검증과 배포
- `validate_outputs.py`: 리포트와 중간 산출물의 품질을 검증한다.
- `publish_to_drive.py`: 검증이 끝난 결과를 Google Drive에 게시한다.

### 4.6 학습과 백테스트
- `train_models.py`: 축적된 CSV를 기반으로 모델 학습을 수행한다.
- `backtest_walkforward.py`: 구간별 워크포워드 검증으로 전략 품질을 평가한다.

## 5. 현재 시스템과의 연결 방식
현재 시스템은 바로 교체하기보다 다음 순서로 분해하는 것이 현실적이다.

1. `schema_registry.csv`와 `validate_csv_contracts.py`를 먼저 만든다.
2. `run_pipeline.py`로 일일 오케스트레이션을 통합한다.
3. `refresh_assumptions.py`, `refresh_eps_cache.py`, `preprocess_daily_updates.py`를 역할별로 쪼갠다.
4. `build_daily_report.py`에서 피처 계산과 점수 산출을 분리한다.
5. `validate_outputs.py`로 검증을 고정한다.

이 순서가 중요한 이유는, 현재 시스템은 이미 돌아가고 있기 때문에 `동작하는 파이프라인을 한 번에 갈아엎는 방식`은 리스크가 크기 때문이다.

## 6. 결론
이번 재분석 기준으로 보면, v1.1 명세의 핵심은 `가능`하다.
다만 구현 전략은 `즉시 전면 교체`가 아니라 `현재 배치 시스템을 기준으로 모듈 분리 + 계약 검증 추가 + 운영 메타화`로 가야 한다.

따라서 결론은 다음과 같다.

- 기술적으로 가능한 범위가 대부분이다.
- 조건부 항목은 데이터 원천과 히스토리 축적이 관건이다.
- DB 전환이나 완전 실시간 자동매매는 이번 범위에서 제외하는 것이 맞다.
- 가장 먼저 해야 할 일은 `schema_registry.csv`와 `validate_csv_contracts.py`를 도입하고, 그 다음 `run_pipeline.py`를 일일 표준 진입점으로 유지하는 것이다.
