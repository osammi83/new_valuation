# 03.new_valuation 프로그램 세부 분석

**작성일**: 2026-04-25  
**목적**: `03.new_valuation` 내 각 프로그램을 더 세밀하게 분해해, AI 재분석과 후속 개발 요청에 바로 활용할 수 있도록 만든 상세 분석 자료다.

---

## 1. 전체 구조를 먼저 읽는 법

이 프로젝트는 다음 4개의 축으로 이해하면 빠르다.

1. **오케스트레이션 축**: PowerShell이 실행 순서와 환경을 제어한다.
2. **데이터 축**: CSV가 사실상의 DB 역할을 한다.
3. **계산 축**: Python이 EPS, 섹터, 기술지표, 점수, 레짐을 계산한다.
4. **배포 축**: 결과를 로컬 output에 저장하고 필요 시 Google Drive로 보낸다.

즉, 이 시스템은 “일일 배치형 CSV 리서치 엔진”이다. 모델 학습형 시스템이 아니라, 규칙과 데이터 정합성을 기반으로 한 운영형 추천 시스템으로 보는 것이 맞다.

---

## 2. 운영 순서

### 2-1. 일일 운영 경로

실제 운영 경로는 다음과 같다.

`run_daily.ps1`
→ `preprocess_daily_updates.py`
→ `refresh_assumptions.py`
→ `build_daily_report.py`
→ (옵션) `upload_to_google_drive.py`

### 2-2. 월간 운영 경로

월간 경로는 다음과 같다.

- `run_eps_cache_refresh.ps1` → `refresh_eps_cache.py`
- `run_assumptions_refresh.ps1` → `refresh_assumptions.py`

### 2-3. 설치/복구 경로

- `install_automation.ps1`는 초기 설치와 스케줄 등록을 담당한다.
- `setup_scheduled_tasks.ps1`는 실제 Task Scheduler 생성기다.
- `remove_scheduled_tasks.ps1`는 제거용이다.
- `set_dart_api_key_env.ps1`, `set_krx_login_env.ps1`는 필수 환경변수 세팅 도구다.
- `check_drive_config.ps1`는 업로드 설정 검증 도구다.

## 3. 프로그램별 세부 분석

### 3-1. `run_daily.ps1`

#### 기능 분해

- 설정 파일 `up_valuation_config.json` 로드
- Python 경로 탐색
- 환경변수 주입
- pip 의존성 설치
- 일일 Python 스크립트 순차 실행
- Google Drive 업로드 옵션 처리

#### 운영상의 의미

이 파일은 단순 실행 스크립트가 아니라 **시스템의 실행 정책**을 담는다. 예를 들어, 여기서 `refresh_assumptions.py`를 끼워 넣은 것은 섹터 구조 복원을 일일 운영으로 끌어온 것이다. 이런 조정 하나가 결과 전체에 영향을 준다.

#### 입력

- `up_valuation_config.json`
- `requirements.txt`
- 사용자/세션 환경변수: `DART_API_KEY`, `KRX_ID`, `KRX_PW`, `UP_VALUATION_PYTHON`

#### 출력

- 직접 파일을 쓰지 않지만 하위 스크립트의 실행 결과를 남긴다.

#### 후속 AI 분석 포인트

- `build_daily_report.py` 중복 호출 여부 확인
- 스크립트가 실패했을 때 어느 단계에서 멈추는지 정리
- `enableGoogleDriveUpload` 조건문이 실제 운영 정책과 맞는지 검토

### 3-2. `run_eps_cache_refresh.ps1`

#### 기능 분해

- Python 경로 선택
- pip install 수행
- `refresh_eps_cache.py` 호출

#### 운영상의 의미

EPS 캐시는 메인 리포트의 핵심 원천 데이터다. 이 파일은 EPS를 일일이 새로 수집하는 대신, 별도 주기에서 무겁게 갱신하도록 분리해둔 안전한 설계다.

#### 후속 AI 분석 포인트

- 강제 갱신과 자연 만료의 구분
- 캐시 병합 시 row identity 기준의 안정성
- DART 우선, 스크랩 fallback, 성장률 fallback의 우선순위 일관성

### 3-3. `run_assumptions_refresh.ps1`

#### 기능 분해

- Python 경로 선택
- pip install 수행
- `refresh_assumptions.py` 호출

#### 운영상의 의미

이 스크립트는 `assumptions.csv`를 universe 기준으로 맞춰 주는 보정기다. 특히 섹터가 `기타`로 고정되는 문제를 완화하는 데 중요하다.

#### 후속 AI 분석 포인트

- 수동 입력값 보존 여부
- sector_group 자동 보정 범위
- assumptions와 universe row mismatch 처리

#### 기능 분해

- Python 실행파일 자동 탐색

#### 후속 AI 분석 포인트

- Python 탐색 순서와 Windows registry 조회 로직
- 사용자가 입력하는 경로 검증 방식
- config 생성 시 비밀정보를 저장하지 않는지 확인

#### 후속 AI 분석 포인트

- 작업명 규칙과 기존 작업 덮어쓰기 정책
- 실행 시간 파라미터의 타임존 해석

#### 후속 AI 분석 포인트

- 키가 없을 때 fallback 동작
- Machine scope 저장 시 권한 문제

#### 후속 AI 분석 포인트

- 공시 키워드 필터 정확성

### 3-11. `refresh_eps_cache.py`

#### 기능 분해

- 캐시 갱신 필요 여부 판단

EPS 캐시는 이 시스템의 가장 중요한 데이터 레이어 중 하나다. 공시와 스크래핑을 함께 사용하되, 공식 데이터 우선이라는 원칙이 분명하다.

#### 후속 AI 분석 포인트

- DART가 없을 때 fallback 품질
- Naver 섹터의 정확도
- 캐시 refresh 주기와 일일 파이프라인의 관계

#### 후속 AI 분석 포인트

- 기타값만 자동 보정하는지 여부
- 수동 sector_group을 덮어쓰지 않는지
- universe에서 빠진 종목 처리 방식

### 3-13. `build_daily_report.py`

#### 기능 분해

- 가격 데이터 로드
- 기술지표 계산
- EPS/밸류 계산
- 시장 레짐 계산
- total_score 산출
- combined_action 부여
- 권장비중 계산
- 출력 파일 생성

#### 현재 구현의 특징

- 시장 레짐은 MA/HV20/ROC60 3신호를 합산해 BULL / NEUTRAL / BEAR를 반환한다.
- `market_regime`과 `regime_weight_multiplier`가 row 단위로 붙는다.
- compact 모드는 핵심 파일만 생성하고, full 모드는 신호성과 요약까지 확장한다.
- `sector_pe_cap`으로 섹터별 밸류 폭주를 제한한다.

#### 운영상의 의미

이 파일은 실제 사용자 눈에 보이는 결과물을 전부 만든다. 따라서 기능 버그가 있으면 곧바로 투자 판단 오류로 이어질 수 있다.

#### 후속 AI 분석 포인트

- `build_final_buy_diff()`와 전일 리포트 비교의 안정성
- 시장 레짐 메타 계산의 통계적 타당성
- `suggested_weight_pct`가 `combined_action`과 항상 일치하는지
- compact/full 파일 생성 조건 차이
- output 잠금 시 fallback 파일명이 해석 가능하게 남는지

## 4. 데이터 파일 세부 역할

### `universe.csv`

분석 대상 종목 마스터다.

- ticker
- name
- market

이 파일이 없으면 모든 파이프라인이 멈춘다.

### `assumptions.csv`

수동 파라미터와 운영자가 제어하는 값이 들어간다.

- is_loss_making
- sector_group
- eps_growth_3y_pct
- target_pe_bear/base/bull
- manual_forward_eps
- max_position_pct

자동값과 수동값의 경계가 이 파일의 핵심이다.

### `eps_cache.csv`

EPS 원천 캐시다.

- trailing_eps_dart
- trailing_eps_scrape
- consensus_eps_scrape
- forward_eps_auto
- naver_sector
- source_primary
- shares_outstanding

실질적으로 밸류 계산의 핵심 입력이다.

### `up_valuation_config.json`

운영 설정 파일이다.

- pythonPath
- enableGoogleDriveUpload
- googleDriveFolderId
- googleServiceAccountJsonPath

### `dart_corp_code_cache.csv`

DART corp code 조회 캐시다.

- stock_code
- corp_code

DART API 호출을 줄이기 위해 존재한다.

## 6. 운영자 관점에서의 실행 방식

### 매일 아침

1. `run_daily.ps1` 자동 실행 확인
2. `상세리포트`와 `핵심근거` 파일 확인
3. `종목선정_핵심근거`에서 상위 종목 검토
4. `warn_flags`와 `brief_reason`으로 위험 점검
5. 필요 시 수동 판단 또는 assumptions 조정

### 매월 1회

1. `run_eps_cache_refresh.ps1` 실행
2. `run_assumptions_refresh.ps1` 실행
3. 섹터, 손실 플래그, EPS 소스 상태 확인
4. Drive/스케줄러 설정 점검

### 장애 시

1. `check_drive_config.ps1`로 업로드 설정 점검
2. `day1_validation_fixed.py`로 리포트 정합성 점검
3. `refresh_eps_cache.py --force --limit N`으로 캐시 복구
4. 필요 시 스케줄러 재등록

AI에게 다음 질문들을 던지면 후속 개발이 빠르다.

- `build_daily_report.py`의 점수식은 현재 너무 보수적/공격적인가?
- 섹터 레짐과 시장 레짐을 별도로 관리할 필요가 있는가?
- EPS-only 기반에서 어떤 품질 지표를 추가해야 하는가?
- output 파일 중 실제로 운영에 쓰이는 파일과 참고 파일은 무엇인가?
- 레거시 경로(`refresh_daily_preprocess.py`, `day1_validation.py`)를 정리할 시점인가?
- Google Drive 업로드를 운영 필수로 둘 것인가, 선택 기능으로 둘 것인가?

## 8. 결론

이 시스템은 다음과 같이 정의할 수 있다.

- **PowerShell이 운영 정책을 관리하고**
- **Python이 계산과 산출물을 만들며**
- **CSV가 상태를 저장하는**
- **운영형 리서치 엔진**이다.

즉, 추가 개발은 단순히 코드를 늘리는 작업이 아니라, **각 파일의 책임을 분명히 나누고, 어떤 데이터가 진실의 원천인지 정하는 작업**이어야 한다.
